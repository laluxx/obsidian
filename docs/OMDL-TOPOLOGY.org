#+TITLE: OMDL Node Graph — Runtime Preparation Contract
#+STARTUP: overview

* Serialized shape and runtime ownership

=OmdlNode= remains the serialized node record. =OmdlSceneGraph.topology_order=
is runtime-only, generated by the loader, owned by the graph, and released by
=omdl_scene_graph_destroy=. Never persist this array in an OMDL file.

=OmdlSceneGraph.bone_override_index= is also runtime-only. The loader builds
stable per-node buckets from each instance's meshes and skin joints after mesh
joint ranges are finalized. Bucket order preserves mesh order and the first
matching joint per mesh, so additive bone overrides keep their prior results.
The per-frame hierarchy pass now visits only overrides for the current node,
instead of scanning every mesh and every skin joint for every node. Index
allocation/build failure retains the original scan; successful graphs perform
no per-frame index allocation.

* Parent/order invariants

- The only legal root sentinel is =-1=.
- Every other parent index is in the same graph's =node_count= range.
- Every node appears exactly once after its parent in the prepared order.
- Cycles, self-parenting, invalid records, and allocation failure leave no usable
  order; animation skips that graph rather than following an invalid chain.
- =obs_node_topological_order= consumes strided records and reads the signed
  parent field bytewise. It is O(N), iterative, and has no internal allocation.

Each frame samples local animation and script offsets, then composes world
matrices once in prepared order. Dirty mesh transforms are published only when
the resulting matrix changes. This contract does not validate the on-disk OMDL
format; Cycle 27 adds that preflight boundary.

Animation sampling currently scans every channel for every node, so phase 1
costs O(nodes × channels), before matching channels perform O(log keyframes)
key lookup. =make bench-animation-channels= exercises the production
=animate_scene= function with synthetic channel/node counts and checks sampled
translations. It includes local sampling and hierarchy composition, but not
GPU work, real asset parsing, morph weights, or Monad dispatch. The measured
cost confirms this is a worthwhile profiling target, not a full-frame estimate:

| Nodes | Channels | Channel checks/frame | Median ns/frame |
|-------+----------+----------------------+-----------------|
| 512 | 0 | 0 | 4,843 |
| 512 | 128 | 65,536 | 82,809 |
| 512 | 512 | 262,144 | 302,184 |
| 1,024 | 1,024 | 1,048,576 | 1,117,934 |
| 2,048 | 2,048 | 4,194,304 | 4,161,160 |

One local GCC =-O2= run, five 16-frame samples per case, with a balanced
parent tree. Treat the values as a
synthetic scaling observation, not a cross-machine baseline or user-visible
frame-time claim. Next optimization must preserve channel order, duplicate
target semantics, and the once-per-frame morph-weight channel behavior.

Transparent meshes use =sort_meshes_by_alpha= when scene topology changes or
the camera moves beyond the existing threshold. Opaque meshes are partitioned
first; blend meshes are ordered back-to-front by squared camera distance.
=make test-transparent-sort= checks ordering and forces the distance cache
=realloc= to fail, verifying the renderer keeps valid opaque/blend counts,
retains the old cache, and sorts successfully on retry. Failed cache growth
leaves blend indices unsorted for that call rather than dereferencing null.

=make bench-transparent-sort= times the production routine, including the
distance pass, for all-blend and 25%-opaque lists. It excludes renderer startup,
GPU work, transform updates, upload, and frame pacing. This GCC =-O2= local
run used five samples of 16 sorts per case:

| Meshes | Blend meshes | Case | Median ns/sort |
|--------+--------------+------+----------------|
| 128 | 128 | all blend | 1,533 |
| 128 | 96 | mixed | 1,112 |
| 512 | 512 | all blend | 12,454 |
| 512 | 384 | mixed | 7,444 |
| 2,048 | 2,048 | all blend | 170,413 |
| 2,048 | 1,536 | mixed | 126,028 |
| 8,192 | 8,192 | all blend | 853,765 |
| 8,192 | 6,144 | mixed | 581,340 |

The sorter uses a fixed Shell-sort gap sequence ending at one. That terminal
insertion-sort pass leaves a quadratic worst case; these deterministic
pseudo-random-depth measurements do not establish a worst-case bound. The
distance cache retains one =float= per mesh-capacity slot (32 KiB at capacity
8,192), and steady-state sorts do not allocate. The 8,192-item result makes
large transparent sets a profiling target; this synthetic run alone does not
justify replacing the algorithm.

The skin-override benchmark compares the former nested lookup with stable
node-index traversal at static, mixed, and fully skinned workload sizes. Its
matrix calculation, hierarchy composition, hardware skinning, Vulkan upload,
and actual frame pacing are outside the measurement. It is CPU-only and not an
FPS result. Live Monad, Vulkan, and GPU animation behavior require their
integration runners and a usable device.

2026-10-12, GCC =-O3 -DNDEBUG=, 5-sample median of 4-frame routing batches:

| Nodes | Meshes | Skinned meshes | Joints/mesh | Nested us/frame | Indexed us/frame | Ratio |
|-------+--------+---------------+-------------+-----------------+------------------+-------|
| 1024 | 256 | 0 | 0 | 90.69 | 0.54 | 168x |
| 1024 | 256 | 32 | 32 | 423.27 | 1.39 | 306x |
| 2048 | 128 | 128 | 64 | 5467.45 | 6.45 | 847x |

The measured nested lookup costs O(nodes × meshes × joints-per-skin);
node buckets reduce steady-state routing to O(nodes + distinct
node/mesh-joint references). Index construction in this fixture took
12.65–76.84 us for these cases; that timing covers the bucket builder, not the
loader's separate reference gathering. For the static case, production exits
before bucket allocation; its 12.65 us figure is harness-only. The persistent
map uses =sizeof(size_t) × (node_count + 1) + 8 × reference_count= bytes on this
64-bit build. These ratios isolate routing and are not predicted frame-time
gains; actual matrix work, override activity, hierarchy composition, and GPU
upload are excluded.
