#+DATE: 2026-10-11
#+STARTUP: overview

* Research conclusion

No single timing source is a complete GPU profiler. Use application timestamps for
repeatable coarse/nested durations, CPU instrumentation for host waits and command
recording, calibrated timestamps for cross-domain timelines when supported, and
vendor tools for hardware-unit counters, queue scheduling, shader stalls and
barrier analysis. Keep detailed hardware-counter captures separate from the
low-overhead benchmark used to compare releases.

* Vulkan timing rules that govern the implementation

- A timestamp query is asynchronous. Its tick-to-nanosecond conversion is
  =delta_ticks * VkPhysicalDeviceLimits::timestampPeriod=; meaningful low bits
  come from the timestamp queue family's =timestampValidBits=. Compute deltas
  modulo that width, including the full-width unsigned wrap case.
- Query timestamps only on a queue family with nonzero =timestampValidBits=.
  A zero value means unsupported. Distinct queue/device timestamps are not a
  common clock and must not be subtracted without an explicit calibration model.
- =vkCmdWriteTimestamp2= has a narrowly specified stage scope, defines an
  execution dependency, and may latch at a logically later stage. Coarse
  TOP_OF_PIPE-to-BOTTOM_OF_PIPE regions are useful approximate pass durations,
  but fine-grained samples and nested intervals need measured overhead and
  careful interpretation. Do not sum nested or overlapping regions as if they
  were exclusive GPU busy time.
- Reuse query slots only after their prior writes are complete. The engine waits
  for the frame-slot fence before collection and does not request blocking query
  reads. This avoids a CPU query-result stall; missing/unavailable query results
  must remain missing, not silently become zero-time work.
- =VK_KHR_calibrated_timestamps= (promoted from =VK_EXT_calibrated_timestamps=)
  provides quasi-simultaneous host/device clock samples plus a maximum deviation.
  It is optional and should be used for cross-domain correlation, not as a
  replacement for same-submit pass deltas. Recalibrate rather than extrapolating
  indefinitely.
- =VK_EXT_debug_utils= object names and nested command labels organize captures
  in RenderDoc and vendor tools; labels do not measure time. Gate detailed
  annotations separately from production timing if they perturb the workload.
- Standard pipeline-statistics queries explain counts (for example shader
  invocations), not elapsed time. =VK_KHR_performance_query= exposes
  implementation-specific counters and may require multiple replay passes. Treat
  both as opt-in diagnostics, not universally available per-frame metrics.

* What external profilers add

- NVIDIA Nsight Graphics GPU Trace: per-queue/event timelines, hardware-unit
  metrics, synchronization visibility and shader sampling/stall attribution.
  Use a short, representative trace after timestamps identify a costly region;
  the trace is a diagnostic capture, not the benchmark baseline. Nsight Systems
  is the complementary CPU/GPU scheduling and submission timeline. Nsight
  Compute is installed, but is not treated as a Vulkan graphics-pass profiler.
- AMD Radeon GPU Profiler: event timing, wavefront occupancy, cache counters and
  barrier timelines can distinguish shader execution from queue/barrier gaps.
  It is not installed/verified on this workstation.
- RenderDoc: frame/event/resource inspection and visual correctness; its timings
  are useful for locating candidate events, not a substitute for hardware-backed
  repeated benchmark measurements.
- Vulkan timestamps answer *how long the measured interval lasted*. They do not
  identify ALU-vs-memory limits, occupancy, cache misses, queue overlap, cause of
  a stall, or competing system activity. Vendor counters/sampling answer those
  questions where available.

* Vendor diagnostic capture recipes

Keep vendor captures separate from release benchmark runs: they may serialize,
replay, inject, or sample and can change execution behavior. The runner's
headless JSON/CSV remains the comparison artifact.

#+begin_src sh
mkdir -p build/bench/vendor
OBSIDIAN_BENCH_ASSET_ROOT=assets \
  nsys profile --trace=vulkan,osrt --sample=none \
  --output=build/bench/vendor/sponza \
  ./obsidian --headless-benchmark build/bench/vendor/sponza.json \
  --monad-boot tests/monad/bench-scene.mon
#+end_src

Nsight Systems CLI records Vulkan API/queue scheduling around the actual
headless Monad-defined Sponza workload. Analyze the `.nsys-rep` timeline for
CPU submission gaps, waits, queue overlap, and expensive API calls; do not
derive performance baselines from this instrumented run. `nsys` is currently
not installed here, so this recipe is documented, not executed.

For Nsight Graphics GPU Trace/Shader Profiler, use a short editor capture on
NVIDIA after the headless timestamp profile identifies a costly pass:

#+begin_src sh
ngfx-capture --exe ./obsidian --working-dir "$PWD" \
  --output-dir build/bench/vendor/nsight-graphics \
  --capture-frame 120 --frame-count 1
#+end_src

This launches the windowed editor and captures a presented frame; it is a
vendor diagnostic, not the headless correctness/performance test. `ngfx-capture`
is not installed here. On a supported AMD system, use Radeon Developer Panel
to capture a Vulkan frame and inspect its `.rgp` in Radeon GPU Profiler. RGP's
frame-based graphics profile is defined around Vulkan applications that call
`Present`; the current headless benchmark does not present, so do not claim that
RGP workflow is headless. RGP/RDP are not installed or verified here.

Nsight Compute CLI 2026.2.1 and RenderDoc CLI 1.45 are installed; RenderDoc is
built with Vulkan support. Nsight Systems, Nsight Graphics Capture CLI and RGP

* Current Obsidian evidence and gaps

- =src/core/gpu_profile.h= now owns one stage schema, hierarchy, and checked
  nanosecond conversion helper. It handles modulo wrap for timestamp widths 1..64
  and rejects invalid widths/periods and overflow. Native tests cover boundaries.
  =src/platform/window.c= collects only after the frame-slot fence without WAIT;
  =src/graphics/vulkan_setup.c= writes same-queue TOP/BOTTOM timestamps. Those
  endpoints are coarse inclusive intervals, not exact exclusive shader durations.
- The schema includes aggregate shadows plus four cascade intervals and aggregate
  HZB plus up to 16 mip intervals. JSON uses the C-owned schema, and Python validates
  IDs, parents, ns units and inclusive semantics before summary/CSV output. The
  dashboard indents children and warns that nested/pipelined durations are
  non-additive. C report serialization and Python schema/metadata tests pass.
- A complete =make -j all= linked after adding the omitted TinyEXR implementation
  object and Monad compiler library to the build. The real headless Sponza profile
  ran 120 warm-up plus 600 measured frames: cascade and HZB-mip values were
  nonzero; unexecuted dynamic geometry/bounds refit and disabled readback were
  null. Raw and summarized JSON contain Vulkan device IDs, driver/API versions,
  queue family, timestamp valid bits and period. Separate headless raw-image smoke
  still produced the expected startup cube. This is integration proof, not a
  stable performance baseline.
- The latest one-process smoke had GPU frame p50 1.463 ms and p95 2.670 ms;
  device-wide GPU utilization was 84-99% at the boundary snapshots. This is
  visibly contaminated/noisy and is not a performance baseline or regression
  threshold.
  Earlier five-process numbers remain historical and were collected before the
  current metadata/scope build; don't mix them as a current controlled baseline.
- CPU command-recording intervals are also exported for render-graph pass
  execution, transmission/transparent recording, and UI recording. One 600-frame
  smoke measured p50 66.6, 10.5, and 1.75 microseconds respectively; outer
  command-record p50 was 111.9 microseconds. These CPU intervals are nested
  inside command recording, not GPU pass durations and not an optimization
  claim.
- Per-run host memory now reports =getrusage.ru_maxrss= peak and Linux
  =/proc/self/statm= resident bytes after engine teardown. One Sponza process
  measured 1288.8 MiB peak and 172.7 MiB final. These are whole-process values,
  not subsystem allocation attribution or GPU heap usage.
- When available, =VK_EXT_memory_budget= reports per-heap =heapUsage= estimates
  before scene loading and before engine teardown plus the final =heapBudget=.
  The Vulkan specification defines usage as an estimate for the current
  process; budget may change with unrelated system activity. These values are
  not Obsidian-only buffer/image accounting. Unsupported devices report no
  heaps. One headless Sponza smoke reported heap-0 1266.1 MiB estimated
  process usage / 9928.0 MiB budget, heap-1 843.1 / 11948.0 MiB, and heap-2
  31.4 / 214.6 MiB. Budget values varied between nearby runs. See the Khronos
  [[https://docs.vulkan.org/refpages/latest/refpages/source/VkPhysicalDeviceMemoryBudgetPropertiesEXT.html][memory-budget property reference]].
- The engine now wraps every direct source-tree =vkAllocateMemory= and
  =vkFreeMemory= call with low-frequency accounting. Per-run
  =engine_vulkan_memory= reports requested =VkDeviceMemory= bytes and live
  allocation counts by physical-device heap: renderer-ready initial state,
  workload final state, and process peak. The runner validates heap ordering,
  nonnegative values, peak bounds, and stable tracking availability; the
  dashboard shows final and peak engine allocations. This is engine-owned
  allocation accounting, not resource-by-resource attribution, resident
  texture bytes, driver overhead, or actual device-local residency. A short
  Sponza smoke recorded heap-0 initial/final/peak 1289.2/1289.2/1289.2 MiB and
  heap-1 840.1/840.1/936.5 MiB. The run proves capture/serialization, not a
  stable footprint baseline. No per-frame polling is added; individual memory
  allocations/frees take a mutex and update a dynamically grown record array.
- Opt-in =VK_EXT_debug_utils= command labels mirror the stage schema, including
  nested shadow cascades and HZB mips. =BENCH_DEBUG_LABELS= defaults to =off=;
  raw JSON records the enabled state and the runner fails if a requested
  capture cannot activate labels. A 600-frame headless Sponza run enabled labels
  on the RTX 3060 and retained required cascade/HZB timing samples. Labels
  organize external captures; they are not a timing source and may perturb
  diagnostic runs. The query pool, graphics command pool/buffers and headless
  color target and primary graphics/SDF/HZB/bounds-refit pipelines also receive
  opt-in debug-utils object names. External capture inspection and broader
  resource names remain open. A headless startup scene passed
  =VK_LAYER_KHRONOS_validation= after teardown exposed and fixed four leaked
  meshlet buffer/memory pairs and a distinct legacy 3D pipeline that had been
  incorrectly treated as an alias. The headless startup smoke now enables
  synchronization validation too. A separate one-process Sponza
  synchronization-validation capture also passed; the benchmark runner scans
  preparation/run logs for validation errors and records diagnostic mode.
  A live Wayland resize validation then exposed an acquire/layout hazard that
  headless validation could not exercise: the =COLOR_ATTACHMENT_OUTPUT=
  semaphore wait did not cover the render graph's =TOP_OF_PIPE= swapchain
  transition. Both windowed submit paths now wait at =TOP_OF_PIPE=. With
  synchronization validation and debug-utils labels enabled, resizing the
  engine through 1280×720, 800×600 and 1440×900 left the window mapped and
  produced no validation diagnostics. This covers settled nonzero sizes, not
  continuous drag pacing, zero-size suspension/restore, or device-loss/error
  injection. The conservative acquire wait can delay unrelated pre-attachment
  GPU work; measure it on a representative workload before claiming resize

- The Monad manifest selects headless scenes; =./make profile= presents a colored
  dashboard and writes JSON/CSV. Performance mode omits host readback; raw-image
  mode retains the copy. CPU phases and lifecycle durations exist. Optional
  CPU-recorded command counters report total and inclusive pass draw calls,
  indirect draw count, directly known vertex/index counts, mesh-task workgroups,

  compute groups sum to the parent/frame totals. These are encoded command

  totals are unknown. Five-process counter-enabled/disabled Sponza runs had
  wall-frame p50 1.398/1.414 ms and CV 27.3/25.6%; this noisy comparison cannot
  establish instrumentation overhead.
- Performance-mode headless rendering now queues up to two frames with
  independent command buffers, color/depth/shadow/HZB/transmission targets and
  timestamp slots. Each frame slot samples its own shadow atlas; sharing a
  writable shadow atlas across queued frames could let one frame overwrite
  shadows while another frame's main pass samples them. The two 2048² D32
  atlases add 32 MiB of logical image texels before Vulkan allocation
  requirements. It waits at slot reuse and collects that slot's timestamps
  only after its fence. Raw-image mode keeps synchronous completion before

  submission-loop medians 1.408/1.241 ms (11.8% lower after) with disjoint
  bootstrap intervals; GPU-frame p50 was 1.209/1.229 ms. This is a throughput
  improvement from CPU/GPU overlap, not a GPU-rendering speedup or a paired
  regression gate. The host frame metric is no longer completion latency.

* Simple-scene GPU memory floor: first measured reductions

The 5-process headless fixture benchmark used
=tests/fixtures/async-triangle.gltf= (1 mesh, 3 vertices, no textures) at
640x360, 120 warm-up frames and 600 measured frames per process. Before this
change, engine-tracked initial Vulkan allocations were 1,332,178,944 bytes on
heap 0 and 880,904,208 bytes on heap 1 (2,213,083,152 bytes total). After
removing an unused 256 MiB device-local dynamic buffer and starting the texture
arena at 4 MiB with geometric growth up to 256 MiB/page, the corresponding
values were 799,502,336 and 880,904,208 bytes (1,680,406,544 total): a
repeatable reduction of 532,676,608 bytes (about 508 MiB). The unused device
buffer had no readers; dynamic uploads copy from the host-visible staging
buffer into the mega vertex buffer. Geometric page growth preserves capacity
for texture-heavy scenes; 64 pages still allow roughly 15.8 GB decimal total
capacity, with each allocation sized for its Vulkan memory requirement.

The 5-run report is
=build/bench/triangle-memory-after/summary.json=. GPU timing is not claimed as
improved: frame CV was 71.3%, and this empty-texture triangle is a memory smoke,
not a representative production scene. =make test= and
=make test-vulkan-validation-headless= passed; the latter rendered the startup
cube with 14,350 visible pixels. The remaining large fixed allocation is the
256 MiB static/dynamic vertex arena. Minimum-footprint work must preserve the
per-frame dynamic-vertex limit and valid device addresses while reducing its
simple-scene reserve. Texture-page growth with real textured and large-image
workloads also needs validation. Meshlet, skin, morph-delta and per-frame bounds
storage now allocate on demand and grow geometrically. Correction: the dynamic
vertex staging arena is
256 MiB because two frame slots each permit 1,048,576 vertices and
=sizeof(Vertex)= is 128 bytes; this is exact for the current hard limit, not
spare 96 MiB.

A follow-up changed the persistent upload staging arena from fixed 64 MiB to
4 MiB initial capacity with checked geometric growth for a larger single
request. The cooked glTF batch path already creates an exact-sized temporary
staging allocation; its preflight now validates the packed batch size rather
than incorrectly requiring the persistent legacy arena to hold the whole
scene. The same five-process triangle workload measured 799,502,336 bytes on
heap 0 and 817,989,648 bytes on heap 1 (1,617,491,984 bytes total), a further
60 MiB reduction and 568 MiB below the original simple-scene baseline. The
native =arena-growth= test covers minimum/geometric/overflow arithmetic; the latest
verified five-process report is
=build/bench/triangle-memory-demand-sized/summary.json=. The rendered
smoke validates the 4 MiB staging base, but no current fixture forces the
Vulkan staging arena's growth branch. Large legacy uploads and texture-heavy
scenes remain required validation workloads. Frame CV was 84.4%; timing is not
claimed as improved.

A further change reduced the initial index arena from 128 MiB to 5 MiB and
added geometric growth that preserves the used index prefix before replacing
the buffer. The triangle fixture used 4,194,316 bytes of indices and reserved
5,242,880 bytes. Five runs measured initial engine-tracked Vulkan allocations
of 670,527,488 bytes on heap 0 and 817,989,648 bytes on heap 1
(1,488,517,136 total): 128,974,848 bytes (123 MiB) below the previous
demand-sized-staging result, and 724,566,016 bytes (691 MiB) below the original
simple-scene baseline. Report: =build/bench/triangle-index-arena/summary.json=.
The smoke workload does not force index-arena growth; native policy tests cover
capacity arithmetic, while a large-geometry Vulkan workload is still needed to
exercise the GPU copy/swap path. =make test= and
=make test-vulkan-validation-headless= passed; the latter rendered the centered
startup cube with 14,350 visible pixels. Frame CV was 74.7%, so timing is not
claimed as improved.

* Lazy morph-delta arena

The fixed 64 MiB device-local morph-delta allocation is now absent until a
scene requests morph data. Its first allocation starts at 4 KiB and grows
geometrically; buffer replacement waits for prior GPU readers, copies the live
delta prefix, updates the shader device address, then retires the old storage.
First allocation skips the device-wide idle wait because no old morph resource
exists. The 200-delta fixture requires 6,400 bytes and logged an 8 KiB
allocation under synchronization validation:
=build/bench/morph-arena-vulkan-final/run-01.log=. That one-process,
10-frame scene smoke exercises the real allocation/upload path, not populated
buffer replacement; a reload workload is still needed to verify live-prefix

* Demand-sized meshlet and bounds arenas

Removed the fixed 16/32/32/64/64 MiB meshlet, static-bounds, skin,
meshlet-vertex and meshlet-triangle pools, plus the two fixed 32 MiB dynamic
bounds buffers. Each is created at a 4 KiB minimum on demand and grows
geometrically; static data growth copies the live prefix and updates its BDA,
while per-frame dynamic bounds are scratch and are recreated without copying.
All geometry preflight and legacy upload paths reserve the matching pools
before writing.

=build/bench/meshlet-arena-vulkan/=. The fixture and native cooker assert

first dynamic-vertex API call reserves the existing two-frame, one-million

* Demand-sized line renderer startup

Line rendering no longer reserves two 256 MiB mapped GPU buffers or a 256 MiB
static CPU array. CPU vertices grow geometrically from 64 vertices; each GPU
frame slot allocates only on upload and grows independently after its fence
retires. Failed uploads do not submit draws with stale storage. Shutdown unmaps
and releases both frame buffers and CPU storage.

* Decision

Do not claim an absolute performance minimum. The measurable finish line is a
reproducible, attribution-capable profiling system with accepted correctness and
regression contracts; optimization continues one evidenced bottleneck at a time.

* Permanent startup attribution and demand-sized immediate vertices

Benchmark reports now include monotonic process-relative startup milestones.
Window runs distinguish GLFW initialization/window creation, input, FreeType,
audio, Vulkan instance/device/swapchain, renderer, Monad runtime, editor and
Monad boot, then first submission and successful present call. A successful
=vkQueuePresentKHR= return is not proof that the compositor displayed the frame.
Unavailable headless stages are null. Terminal summaries label window mode
correctly and print the measured stages.

Default application startup no longer loads five unused demo textures or the
unused 4K rock material. IBL and actual editor resources remain intact.
The normal-window benchmark now captures engine allocation sizes and Vulkan
heap estimates before application setup and before teardown.

Immediate vertices grow from 64 vertices per frame to the existing one-million
vertex limit instead of allocating that limit on first use. All upload and draw
addresses use the actual frame stride. Growth retires GPU users, retains the
current CPU frame prefix, and publishes mapped staging only after replacement
allocation/map succeeds. Growth currently uses a device-idle wait; eliminating
that wait requires a separately verified retirement design.

Five fresh-process 800x600 window runs, ten warmup and thirty measured frames:
=build/bench/window-dynamic-demand/summary.json=. Median first successful
present call was 524.328 ms; GLFW window creation milestone 163.137 ms;
renderer-ready 409.640 ms. Tracked final device heap allocations were 165.3 MiB
and host heap allocations 12.2 MiB, versus 691.6/268.1 MiB before demand-sizing.
Whole-process peak RSS median was 419.7 MiB. Sequential runs and differing frame
counts do not establish a controlled timing speedup.

=make obsidian=, =make test= and =make test-vulkan-validation-headless= passed.
The raw headless cube retained center RGBA (178,178,178,255) and 14,350 visible
pixels. Window rendering exercised dynamic growth across forty frames per
process. A separate throwaway headless C smoke exercised 65, 4,097, 17, 65,537,
513 and 1,048,576 vertices across both frame slots, checking retained vertex
values after every append and drawing static cubes between growth transitions.
It emitted raw image data and passed synchronization validation with no
validation errors; the layer reported a deprecated environment-setting warning.
The temporary source/build target were removed. Subsequent permanent native
contracts now cover replacement map failure/retry, preserved write cursor and
vertex prefix, maximum capacity, and alternating frame ownership between two
real windows. Run =make test-vulkan-dynamic-headless= and
=make test-vulkan-dynamic-window=. Both passed with synchronization validation.
Their Python contract runner fails on validation diagnostics even when the
native executable returns success.

The multi-window contract exposed three leaked render-finished semaphores in
=obs_window_destroy=. Window destruction now retires presentations, destroys
those semaphores and frees per-image fence bookkeeping before swapchain teardown
resets the image count. The failing-before/passing-after real Vulkan contract
retains this regression coverage.

* Constructor ownership and alternating startup controls

Tracked allocations now retain constructor ownership, live/peak bytes and
live/peak allocation counts. Shared buffer allocation preserves its caller's
constructor name; direct allocations retain their allocating function name.
This is constructor-level attribution, not asset/object identity or driver
internal memory. Unlabeled allocations are explicitly =unknown=. Owner names
are copied, allocation failures do not enter accounting, and reports fail
closed if owner capacity or accounting overflows. The benchmark schema checks
that summed owner live bytes/counts equal summed heap live bytes/counts.

The older =build/bench/window-owner-attribution/summary.json= recorded 99.1
MiB of IBL images and 12.0 MiB of texture pages. A fresh profile later exposed
that the default demo also loaded unused textures: the reproducible baseline
=build/bench/ibl-f32-baseline-current/summary.json= attributed 552.2 MiB to
texture pages. That older 12.0 MiB figure is not representative of the current
default demo startup.

* Default-window memory reduction and Vulkan validation findings

The live-window benchmark now activates the same GPU-allocation and startup
memory trackers as the headless path, samples them after window initialization,
and captures final GPU memory after device idle. Before that correction the
window report omitted process-entry memory and undercounted allocations.

The default demo loaded five unused texture assets and an unused 4K rock
material. Removing those loads, while explicitly preserving the material reset
they incidentally performed, reduced texture-page memory. A second reduction
uses RGBA16F storage images for the environment, irradiance, and prefiltered
IBL outputs when the device supports the required storage, sampling, filtering,
and transfer features. HDR input and compute arithmetic remain FP32; devices
without the optional storage feature retain the RGBA32F path. The cache uses a
distinct OIB2 header for the half-float payload, so an older cache is rebaked
once on a capable device rather than read with the wrong pixel size.

One-run, 10-frame profiles on the RTX 3060, 800x600 default editor workload:

| Metric | FP32 baseline | Optimized cache hit |
|--------+---------------+---------------------|
| Texture-page owner live | 552.2 MiB | 4.2 MiB |
| IBL-image owner live | 99.1 MiB | 50.1 MiB |
| Engine-tracked GPU live allocations, all heaps | 714.7 MiB | 117.7 MiB |

Tracked live GPU allocation fell by 626,032,640 bytes (597.0 MiB, 83.5%).
Reports: =build/bench/ibl-f32-baseline-current/summary.json= and
=build/bench/ibl-fp16-window-cache-hit/summary.json=. These are one-run memory
measurements, not a statistically controlled timing comparison. The isolated
cache-miss run validated a real RGBA16F bake and cache write:
=build/bench/ibl-fp16-window-cache-miss/summary.json= reports zero Vulkan
validation errors. The bake has a higher temporary peak than a cache hit
(178.1 MiB attributed peak for IBL images); steady-state IBL live memory is
50.1 MiB.

That real-window validation run also exposed correctness faults, now covered
by permanent tests:

- The first swapchain-image layout barrier did not match the acquire-semaphore
  wait stage. Acquired images now enter the render graph with
  COLOR_ATTACHMENT_OUTPUT as the source stage.
- IBL image transitions lacked transfer-read access for cache readback.
  Transition access masks now cover transfer and shader layouts.
- Dynamic-geometry copies used the configured maximum vertex count rather than
  the allocated per-frame staging stride. Every per-frame offset now derives
  from that stride; buffer growth relocates each frame slice so changing the
  stride preserves both frames' data.

* Sponza frame baseline and texture-page regression

* Animation-channel indexing optimization

CPU sampling of the production animation benchmark captured 687 samples with
zero lost samples; =animate_scene= accounted for 98.66% of self samples. The
production function scanned every animation channel for every node even
though each channel targets one node. Added a runtime-only stable node-to-
channel index for large animations (more than 4096 legacy node/channel checks).
It is built once per immutable animation graph, preserves channel order,
indexes morph-weight channels separately, and falls back to the original scan
if allocation fails. Small animations retain the no-index path; no per-frame
allocation or serialized-format change.

The same CPU-only benchmark executable, 256 frames per sample and five
samples, compared before/after hot medians:

| Nodes × channels | Before | After | Change |
|------------------+--------+-------+--------|
| 512 × 128 | 79.6 µs | 9.2 µs | 8.7× faster |
| 512 × 512 | 280.8 µs | 21.3 µs | 13.2× faster |
| 1024 × 1024 | 1.014 ms | 42.6 µs | 23.8× faster |
| 2048 × 2048 | 3.899 ms | 86.1 µs | 45.3× faster |

At 2048 × 2048 the first indexed call measured 132.6 µs, including index
construction; subsequent hot median was 86.1 µs/frame. The 512-node,
zero-channel case remained 4.7 µs/frame. Regression coverage checks stable
ordering for repeated node targets, translation/rotation/scale composition,
morph weights, and hierarchy output against the reference path.
These synthetic animation sizes are not measured Sponza frame costs.

* Transparent-sort large-blend optimization

The production CPU-only transparent-sort benchmark measured the full partition,
distance-cache, and sort path (five samples × 256 sorts; median per sort).
Replacing Shell sort at large blend counts with an in-place min-heapsort
improved the large cases without extra scratch allocation. Shell sort remains
for fewer than 2048 blended meshes, preserving the existing path at small
sizes. The measured 2048-item all-blend case is the smallest benchmarked size
where the heapsort path showed a clear gain; the crossover between algorithms
was not exhaustively searched.

| Meshes | Blend meshes | Before | After | Change |
|--------+--------------+--------+-------+--------|
| 128 | 128 | 1.50 µs | 1.35 µs | 10% faster |
| 512 | 512 | 9.74 µs | 9.70 µs | 0.4% faster |
| 2048 | 2048 | 160.4 µs | 118.5 µs | 26% faster |
| 8192 | 8192 | 766.5 µs | 673.5 µs | 12% faster |
| 8192 | 6144 | 560.8 µs | 477.0 µs | 15% faster |

For at least 2048 blended items, the path now has O(n log n) comparison work;
smaller blends retain the existing Shell sort. Sorting runs only when scene
topology or camera position changes, so these are update-spike savings, not a
per-frame reduction. These are synthetic CPU workloads, not measured Sponza
transparent meshes. Equal-distance tie order is not stable in either algorithm;
the contract and regression check require depth order and complete membership,
not a specific permutation of ties. Full benchmark output is produced by
=make bench-transparent-sort BENCH_ITERATIONS=256=.

* Static shadow-atlas reuse

The Sponza baseline showed four stable cascades at 1280x720: aggregate shadow
GPU p50 0.553 ms (p95 0.620 ms), 20.5% of the 2.694 ms GPU-frame p50. A CPU
whole-mesh AABB cull was rejected: all 103 meshes overlapped every cascade,
and the profile remained 0.555 ms with the same 412 draws / 688 mesh-task
groups. Moving task-shader plane extraction to one invocation and sharing the
mesh normal matrix also did not improve measured GPU time; the latter regressed
the forward pass. Neither experiment is retained.

Static shadow maps are now reused independently per in-flight frame slot. A
fingerprint covers cascade matrices, scene revisions, each eligible caster's
model/bounds/meshlet ranges, alpha-test material inputs, and texture image/view
handles. A hit imports the atlas from its actual shader-read layout and loads
the existing depth attachment instead of clearing/rasterizing four cascades.
Skinned and morphed casters, disabled shadows, and empty draw lists bypass the
cache; unsafe frames invalidate both slots after successful submission.
Transform, bounds, material, texture-handle, or cascade changes produce a
different key. Textures are treated as immutable once their VkImage/view is
created; adding in-place texture painting needs an explicit texture revision in
the cache key.

Using the same five-process/30-warmup/60-measured cold-Sponza workload, the
baseline shadow pass had 103 mesh draws and 172 task groups per cascade. In
the cache run, steady-state headless frames contained no shadow pass timestamp
and no shadow Vulkan draw/task commands; only the main-forward work remained.
GPU-frame p50 was 0.724 ms (run-level wall p50 0.768 ms; frame CV 40.8%).
This is not a clean whole-frame A/B: the baseline had work counters disabled,
the cache run enabled them, and external GPU load was high. The direct evidence
is that steady-state static frames omit the previously measured 0.553 ms shadow
pass; the frame-p50 change is directional, not an isolated causal estimate.
Synchronization validation passed for repeated atlas LOAD/read transitions.
That smoke exposed a render-graph contract bug: load attachments require read
access as well as write access in their dependency. Color and depth attachment
dependencies now include the corresponding read bit when =clear=false=, with a
native contract test for both.

The cache-key native test covers model/cascade/bounds/revision/material/texture
changes and skinned/morphed bypass. Full report:
=build/bench/sponza-shadow-cache-final/summary.json=; validation smoke:
=build/bench/sponza-shadow-cache-final-validation/summary.json=.
